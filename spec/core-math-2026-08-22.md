# CORE-MATH scalar corpus contract

This document defines schema version 1 of the scalar oracle corpus.
The contract applies only to `zmath-testing`.
The `zmath` runtime must not depend on CORE-MATH, MPFR, Arb, GMP, or FLINT.

## Pinned inputs

Schema version 1 pins these inputs:

| Item | Required value |
| --- | --- |
| CORE-MATH repository | `https://gitlab.inria.fr/core-math/core-math.git` |
| CORE-MATH revision | `3bafed75e3c22399531857d63a3fa0e24bfb42fa` |
| MPFR precision | 512 bits |
| Arb precision | 512 bits |
| Rounding policy | `nearest_even` |

The CORE-MATH revision is an immutable 40-digit lowercase commit identifier.
A branch, tag, abbreviated commit, or moving reference is invalid.
The pin identifies the upstream source baseline.
It does not state that `zmath` implements an upstream function.

MPFR produces a candidate at 512-bit precision with `MPFR_RNDN`.
Conversion to the target format also uses `MPFR_RNDN`.
Arb evaluates the same finite input at 512-bit precision.
The complete Arb interval must round to one target bit pattern.
The MPFR candidate and the Arb result must agree on that pattern.
The producer must fail if either oracle cannot decide, if the interval spans a rounding boundary, or if the results differ.
The producer must not increase precision silently or write a best-effort row.
A later precision change requires a new schema version.

## Formats

Schema version 1 accepts only these exact format identifiers:

| Identifier | IEEE 754 format | Width | Hexadecimal digits |
| --- | --- | ---: | ---: |
| `h` | binary16 | 16 bits | 4 |
| `f` | binary32 | 32 bits | 8 |
| `d` | binary64 | 64 bits | 16 |

The identifier `q` is reserved for a future binary128 contract.
Schema version 1 must reject `q`.
Schema version 1 must reject `bfloat16`.
It must also reject aliases, uppercase identifiers, and all unknown identifiers.

## Manifest schema

`zmath-testing/test/corpus/manifest.toml` is the machine-readable manifest.
A schema version 1 parser must require these root keys with the exact values in the manifest:

- `schema_version`
- `core_math_repository`
- `core_math_revision`
- `mpfr_precision_bits`
- `arb_precision_bits`
- `rounding`
- `formats`
- `reserved_formats`
- `rejected_formats`
- `columns`
- `hexadecimal`
- `uncertainty_policy`

The parser must reject a missing key, an unknown key, or a duplicate key.
The parser must reject duplicate function rows.
Each `[[function]]` row has exactly three keys: `op`, `format`, and `status`.
The allowed operations are `exp`, `log`, and `sin`.
The allowed status values are `unsupported`, `correct`, and `bounded`.

`correct` requires a correctly rounded result in the `nearest_even` policy.
`bounded` permits the finite-result ULP limit in the corpus row and applies only in `nearest_even`.
`unsupported` states that no public implementation or accepted corpus exists.
An `unsupported` row must not name a symbol or a corpus file.
A status change requires implementation, oracle evidence, and a manifest update.
The initial manifest contains nine unsupported rows in operation order and H/F/D format order.

## `exp` status transition evidence

The `exp` rows remain `unsupported` until reviewers accept all evidence in this section.
Evidence for one format does not change the status of another format.

The initial Exp API has one nearest-even contract for each format:

- `exph(x: f16) f16`
- `expf(x: f32) f32`
- `expd(x: f64) f64`

These signatures do not take a `RoundMode` argument. The initial Exp API supports `nearest_even` only. Other rounding modes are unsupported for initial Exp. The manifest records this policy for every `exp` row.

Use this checklist for each proposed `correct` or `bounded` transition:

- [ ] Put the dependency-free algorithm in `zmath/src/scalar.zig`.
- [ ] Identify the public symbol as `exph`, `expf`, or `expd`.
- [ ] Show that the implementation does not call host libm or read the process floating-point environment.
- [ ] Approve the exact special-value bit table below for the format.
- [ ] Declare an explicit allowlist of supported target triples and Zig optimization modes. Do not infer support for an unlisted target or mode.
- [ ] Support only `nearest_even` with gradual underflow under schema version 1.
- [ ] For H, validate all 65,536 binary16 input patterns exactly once.
- [ ] For F or D, accept a hard-case corpus with exact input and expected output bits.
- [ ] Include zeros, infinities, NaNs, overflow edges, underflow edges, and subnormal boundaries in each applicable corpus.
- [ ] Include reduction boundaries, rounding midpoints, and the adjacent representable inputs in each F or D hard-case corpus.
- [ ] Generate each finite oracle result with MPFR at exactly 512 bits and `MPFR_RNDN`.
- [ ] Prove with a 512-bit Arb interval that each finite oracle result rounds to the same target bits.
- [ ] Reject a row when MPFR and Arb disagree or when the Arb interval crosses a rounding boundary.
- [ ] Accept a repository-relative benchmark corpus path, its input selection rule, and its input count.
- [ ] Record benchmark results for every supported target and Zig optimization mode.
- [ ] For `correct`, set every corpus `max_ulp` value to `0`.
- [ ] For `bounded`, approve one finite-result ULP limit before the status change.

The exact `exp` special-value table is:

| Format | `+0` input to output | `-0` input to output | `+infinity` input to output | `-infinity` input to output | Any NaN input `b` to output |
| --- | --- | --- | --- | --- | --- |
| `h` | `0000` to `3c00` | `8000` to `3c00` | `7c00` to `7c00` | `fc00` to `0000` | `b OR 0200` |
| `f` | `00000000` to `3f800000` | `80000000` to `3f800000` | `7f800000` to `7f800000` | `ff800000` to `00000000` | `b OR 00400000` |
| `d` | `0000000000000000` to `3ff0000000000000` | `8000000000000000` to `3ff0000000000000` | `7ff0000000000000` to `7ff0000000000000` | `fff0000000000000` to `0000000000000000` | `b OR 0008000000000000` |

The H corpus is exhaustive evidence, not a sample or benchmark substitute.
The F and D hard-case corpora must name their generation method and immutable artifact paths.
The benchmark corpus measures performance only and cannot replace correctness evidence.
The manifest row must remain `unsupported` while any checklist item is missing or disputed.

## TSV schema

A future corpus file uses UTF-8 text without a byte-order mark.
It uses LF line endings and ends with one LF.
It has one header and no blank lines or comments.
The header contains these tab-separated column names in this order:

```text
op	format	input_bits	output_bits	output_class	max_ulp
```

Each data row has exactly six tab-separated fields:

| Column | Rule |
| --- | --- |
| `op` | One of `exp`, `log`, or `sin` |
| `format` | One of `h`, `f`, or `d` |
| `input_bits` | Exact fixed-width input bits |
| `output_bits` | Exact fixed-width expected output bits |
| `output_class` | One of `normal`, `subnormal`, `zero`, `infinity`, or `qnan` |
| `max_ulp` | A canonical unsigned decimal integer |

Bit strings contain lowercase hexadecimal digits without a `0x` prefix.
Each string has the width required by its format.
Leading zeroes are required.
A parser must reject uppercase digits, signs, separators, prefixes, and incorrect widths.

`max_ulp` uses `0` or a nonzero value without a leading zero.
A `correct` function row requires `max_ulp` equal to `0`.
Special-value rows always use `max_ulp` equal to `0` and require an exact bit match.

Rows use manifest operation order, then manifest format order, then unsigned numeric `input_bits` order.
The tuple `(op, format, input_bits)` must be unique across the complete corpus.
A producer must fail on a duplicate.
A consumer must reject an unsorted or duplicate corpus.

## Exact rounding policy

For a finite mathematical result, round once to the target format.
Use round-to-nearest with ties to an even least-significant significand bit.
Use gradual underflow.
Do not flush subnormal values to zero.
Overflow follows IEEE 754 round-to-nearest behavior.
A nonzero result that rounds to zero keeps the sign of the exact result.
The process floating-point environment must not change this policy.

`output_bits` is the expected oracle pattern for every row.
For a `correct` function row, the consumer requires an exact match for every output class.
For a `bounded` function row, the consumer requires an exact match for special values and a ULP distance no greater than `max_ulp` for finite normal or subnormal values.
The ULP distance applies only when both finite results have the same sign. A sign difference fails.

## Special values

These encodings are exact:

| Format | `+0` | `-0` | `+1` | `+infinity` | `-infinity` | Canonical quiet NaN |
| --- | --- | --- | --- | --- | --- | --- |
| `h` | `0000` | `8000` | `3c00` | `7c00` | `fc00` | `7e00` |
| `f` | `00000000` | `80000000` | `3f800000` | `7f800000` | `ff800000` | `7fc00000` |
| `d` | `0000000000000000` | `8000000000000000` | `3ff0000000000000` | `7ff0000000000000` | `fff0000000000000` | `7ff8000000000000` |

For a NaN input, preserve the sign and all payload bits.
Set the quiet bit in the output.
The quiet-bit masks are `0200`, `00400000`, and `0008000000000000` for H, F, and D.
Thus, the required output is the input bit pattern OR the format quiet-bit mask.
A quiet NaN remains unchanged.
A signaling NaN becomes a quiet NaN.

An invalid non-NaN input produces the positive canonical quiet NaN for its format.
No corpus output may encode a signaling NaN.
The `qnan` class requires an exact match of the sign, quiet bit, and payload.

The operation rules are:

| Operation | Exact special-value behavior |
| --- | --- |
| `exp` | `exp(+0)` and `exp(-0)` are `+1`. `exp(+infinity)` is `+infinity`. `exp(-infinity)` is `+0`. |
| `log` | `log(+0)` and `log(-0)` are `-infinity`. `log(+1)` is `+0`. `log(+infinity)` is `+infinity`. A negative non-NaN input produces the canonical quiet NaN. |
| `sin` | `sin(+0)` is `+0`. `sin(-0)` is `-0`. Either infinity produces the canonical quiet NaN. |

The NaN-input rule takes precedence over each operation rule.
The producer encodes exact constants directly and does not ask a host library to choose their bits.

## Fail-closed rules

A producer must stop without changing corpus files when any required fact is uncertain.
Uncertainty includes an oracle disagreement, an Arb interval that spans two target results, and an unknown special-value policy.
A consumer must reject a corpus that disagrees with this document or its manifest.
It must not skip a bad row, substitute a host result, or accept a nearby value.

All nine initial function-format rows are `unsupported`.
Therefore, schema version 1 defines no implemented transcendental function and accepts no transcendental corpus data.
