# CORE-MATH scalar corpus contract

This document defines schema version 1 of the scalar oracle corpus.
The contract applies only to `zmath-testing`.
The `zmath` runtime must not depend on CORE-MATH, MPFR, Arb, GMP, or FLINT.

## Pinned inputs

Schema version 1 pins these inputs:

| Item | Required value |
| --- | --- |
| CORE-MATH repository | `https://gitlab.inria.fr/core-math/core-math.git` |
| CORE-MATH revision | `3bafed75e3c22399531857d63a3fa0e24bfb42fa` |
| MPFR precision | 512 bits |
| Arb precision | 512 bits |
| Rounding policy | `nearest_even` |

The CORE-MATH revision is an immutable 40-digit lowercase commit identifier.
A branch, tag, abbreviated commit, or moving reference is invalid.
The pin identifies the upstream source baseline.
It does not state that `zmath` implements an upstream function.

MPFR produces a candidate at 512-bit precision with `MPFR_RNDN`.
Conversion to the target format also uses `MPFR_RNDN`.
Arb evaluates the same finite input at 512-bit precision.
The complete Arb interval must round to one target bit pattern.
The MPFR candidate and the Arb result must agree on that pattern.
The producer must fail if either oracle cannot decide, if the interval spans a rounding boundary, or if the results differ.
The producer must not increase precision silently or write a best-effort row.
A later precision change requires a new schema version.

## Formats

Schema version 1 accepts only these exact format identifiers:

| Identifier | IEEE 754 format | Width | Hexadecimal digits |
| --- | --- | ---: | ---: |
| `h` | binary16 | 16 bits | 4 |
| `f` | binary32 | 32 bits | 8 |
| `d` | binary64 | 64 bits | 16 |

The identifier `q` is outside this contract.
Schema version 1 must reject `q`.
Schema version 1 must reject `bfloat16`.
It must also reject aliases, uppercase identifiers, and all unknown identifiers.

## Target C23 scalar family

This section defines the target `zmath` scalar names. It does not grant implementation or manifest acceptance.

### Independent status terms

The contract keeps these facts separate:

- **Target** means that a root generic and its suffixed scalar names are required by this API.
- **Implemented** means that the current source exports the suffixed symbol.
- **Manifest-accepted** means that an operation-format row has status `correct` or `bounded`.

A target symbol is not necessarily implemented. An implemented symbol is not necessarily manifest-accepted.

Schema version 1 has manifest rows only for `exp`, `log`, and `sin`. All nine initial rows start as `unsupported`.
An `unsupported` row does not state that its implementation is absent.
No source directory, planned symbol, or CORE-MATH function proves manifest acceptance.

### Implemented-source snapshot

The current source exports these IEEE symbols:

```text
RoundMode Class
toBitsh fromBitsh
classifyh classifyf classifyd
copySignh copySignf copySignd
nextUph nextDownh
nextAfterh nextAfterf nextAfterd
scaleBh roundIntegralh
totalOrderh totalOrderf totalOrderd
```

The current source exports these scalar symbols:

```text
logd sind cosd
exph logh sinh cosh logf
absh absf absd
ulpDistanceh ulpDistancef ulpDistanced
expf expd sinf cosf
```

These exports do not imply a target generic root export or manifest acceptance.

### Generic dispatch

The public root generic is `zmath.<op>`. Its floating argument type selects one exact suffixed scalar symbol:

| Floating type | Suffix |
| --- | --- |
| `f16` | `h` |
| `f32` | `f` |
| `f64` | `d` |

For a normal operation, all floating arguments have the same type. Dispatch does not widen, narrow, or coerce them.
The scalar symbol is the operation name followed by the suffix. Thus, `exp{h,f,d}` means `exph`, `expf`, and `expd`.

The existing `sinh`, `sinf`, and `sind` symbols are the sine family.
The target hyperbolic symbols are `sinhh`, `sinhf`, and `sinhd`.
The existing `cosh`, `cosf`, and `cosd` symbols are the cosine family.
The target hyperbolic cosine symbols are `coshh`, `coshf`, and `coshd`.
The target tangent symbols are `tanh`, `tanf`, and `tand`.
The target hyperbolic tangent symbols are `tanhh`, `tanhf`, and `tanhd`.

`zmath.abs` is the C23 `fabs` operation. Its scalar names remain `absh`, `absf`, and `absd`.
The target has no `fabs`, `fabsh`, `fabsf`, or `fabsd` aliases.

The target has no `q`, `f128`, bfloat16, decimal, or long-double family.
Generic dispatch rejects those types.

### Caller rounding precondition

Callers must keep IEEE round-to-nearest, ties-to-even active for each scalar call.
`zmath` does not read, validate, set, or restore the process floating-point environment (`fenv`).
Behavior under another active rounding mode is unsupported.

An operation-defined direction argument, such as the `fromfp` direction, does not change the process environment.
Narrowing operations compute as if to infinite precision and round once to the declared destination type.

### Basic and rounding family

Each operation below has one root generic and the `h`, `f`, and `d` scalar names:

```text
abs ceil floor nearbyint rint round roundeven trunc
lrint llrint lround llround
fromfp ufromfp fromfpx ufromfpx
```

`fromfp` and `fromfpx` return signed integer results. `ufromfp` and `ufromfpx` return unsigned integer results.
Their suffix is selected by the floating input. Their C23 rounding-direction and width arguments remain explicit.

### Exponential and logarithmic family

```text
exp exp2 exp10 expm1 exp2m1 exp10m1
log log2 log10 log1p logp1 log2p1 log10p1
```

`log1p` and `logp1` are separate public spellings for the same mathematical operation.

### Trigonometric, inverse, and pi-scaled family

```text
sin cos tan asin acos atan atan2
sinpi cospi tanpi asinpi acospi atanpi atan2pi
```

### Hyperbolic and inverse hyperbolic family

```text
sinh cosh tanh asinh acosh atanh
```

The suffix rule applies to every name in this list. Hyperbolic H names use the operation-plus-suffix spelling, such as `sinhh`.
The H symbols are `sinhh`, `coshh`, `tanhh`, `asinhh`, `acoshh`, and `atanhh`.

### Power, root, and norm family

```text
pow pown powr compoundn sqrt cbrt rsqrt rootn hypot
```

`compoundn`, `pown`, and `rootn` use the C23 `long long int` exponent or degree.
The zmath mapping is `i64`. `compoundn(x, n)` computes `(1 + x)^n`.

The pinned CORE-MATH `compound` source takes a floating exponent in its direct implementation.
It is not direct evidence for the C23 `compoundn` contract.

### Error and gamma family

```text
erf erfc lgamma tgamma
```

`lgamma` returns `LgammaResult(T) { value: T, sign: i2 }`.
The root generic and all suffix variants use this result shape.
The API has no global `signgam` object and no hidden mutable gamma-sign state.

### Remainder, decomposition, and scaling family

```text
fmod remainder remquo
frexp modf ilogb llogb logb ldexp scalbn scalbln
```

The zmath result containers replace C output pointers for `frexp`, `modf`, and `remquo`.
The mathematical result and integer side result keep the C23 meanings.

### Fused, difference, maximum, and minimum family

```text
fma fdim fmax fmin
fmaximum fminimum
fmaximum_mag fminimum_mag
fmaximum_num fminimum_num
fmaximum_mag_num fminimum_mag_num
```

The `fmax` and `fmin` families keep their C23 NaN and signed-zero rules.
The `fmaximum` and `fminimum` families use the IEC 60559 maximum and minimum relations.
The magnitude and number variants apply their C23 relation after selecting the operation family.

### Narrowing family

C23 7.12.14 defines these binary-format functions:

```zig
pub fn fadd(x: f64, y: f64) f32;
pub fn fsub(x: f64, y: f64) f32;
pub fn fmul(x: f64, y: f64) f32;
pub fn fdiv(x: f64, y: f64) f32;
pub fn ffma(x: f64, y: f64, z: f64) f32;
pub fn fsqrt(x: f64) f32;
```

For supported IEC 60559 formats, the C23 Annex F forms are:

```text
f16addf32  f16subf32  f16mulf32  f16divf32  f16fmaf32  f16sqrtf32
f16addf64  f16subf64  f16mulf64  f16divf64  f16fmaf64  f16sqrtf64
f32addf64  f32subf64  f32mulf64  f32divf64  f32fmaf64  f32sqrtf64
```

For example, `f16addf32(f32, f32) f16`, `f32fmaf64(f64, f64, f64) f32`, and `f16sqrtf64(f64) f16`.
These names encode the destination before the source. They are not same-type generic operations.

The target omits all `_FloatNx`, `q`, `f128`, bfloat16, decimal, and long-double forms.

### Optional IEC 60559 extension family

C23 Annex F makes these operations optional extensions outside baseline 7.12:

```text
totalOrderMag getPayload setPayload setPayloadSig
```

The target suffix families are `totalOrderMag{h,f,d}`, `getPayload{h,f,d}`, `setPayload{h,f,d}`, and `setPayloadSig{h,f,d}`.
Each has one root generic with the same operation name.
No symbol in this optional family is implemented or manifest-accepted in this contract revision.

### Special-value policy

The oracle and implementation must use exact target-format bit patterns.
The format encodings are:

| Format | `+0` | `-0` | `+1` | `+infinity` | `-infinity` | Canonical quiet NaN |
| --- | --- | --- | --- | --- | --- | --- |
| `h` | `0000` | `8000` | `3c00` | `7c00` | `fc00` | `7e00` |
| `f` | `00000000` | `80000000` | `3f800000` | `7f800000` | `ff800000` | `7fc00000` |
| `d` | `0000000000000000` | `8000000000000000` | `3ff0000000000000` | `7ff0000000000000` | `fff0000000000000` | `7ff8000000000000` |

For a NaN input, preserve the sign and payload and set the format quiet bit.
The quiet-bit masks are `0200`, `00400000`, and `0008000000000000` for `h`, `f`, and `d`.
A quiet NaN remains unchanged. A signaling NaN becomes a quiet NaN.

Unless an operation has a stricter C23 rule, the first NaN argument in parameter order selects the result.
An invalid non-NaN input returns the positive canonical quiet NaN for its format.
An operation-specific C23 rule takes precedence over this default.

`exp`, `log`, and `sin` use the exact special tables in this document.
The maximum, minimum, magnitude, and number families use their specified C23 or IEC 60559 NaN and signed-zero relations.
The producer writes exact constants directly and does not ask a host library to choose special-value bits.


## Manifest schema

`zmath-testing/test/corpus/manifest.toml` is the machine-readable manifest.
A schema version 1 parser must require these root keys with the exact values in the manifest:

- `schema_version`
- `core_math_repository`
- `core_math_revision`
- `mpfr_precision_bits`
- `arb_precision_bits`
- `rounding`
- `formats`
- `reserved_formats`
- `rejected_formats`
- `columns`
- `hexadecimal`
- `uncertainty_policy`

The parser must reject a missing key, an unknown key, or a duplicate key.
The parser must reject duplicate function rows.
Each `[[function]]` row has exactly three keys: `op`, `format`, and `status`.
For the schema version 1 initial corpus, the allowed operations are `exp`, `log`, and `sin`.
The allowed status values are `unsupported`, `correct`, and `bounded`.

`correct` requires a correctly rounded result in the `nearest_even` policy.
`bounded` permits the finite-result ULP limit in the corpus row and applies only in `nearest_even`.
`unsupported` states that the manifest has no accepted accuracy claim for the pair. It does not state that an implementation is absent.
An `unsupported` row must not name a symbol or a corpus file.
A row can change from `unsupported` to `correct` or `bounded` only after implementation, oracle evidence, and a manifest update.
The initial manifest contains nine unsupported rows in operation order and H/F/D format order.

## Initial Exp, Log, and Sin API

Each initial Exp, Log, and Sin function has one scalar argument and uses a lower-case H/F/D suffix:

```zig
pub fn exph(x: f16) f16;
pub fn expf(x: f32) f32;
pub fn expd(x: f64) f64;
pub fn logh(x: f16) f16;
pub fn logf(x: f32) f32;
pub fn logd(x: f64) f64;
pub fn sinh(x: f16) f16;
pub fn sinf(x: f32) f32;
pub fn sind(x: f64) f64;
```

These signatures do not take a `RoundMode` argument. Callers must keep IEEE round-to-nearest, ties-to-even active for each call. `zmath` does not read, validate, set, or restore the process floating-point environment (`fenv`). Behavior under other rounding modes is unsupported.

The initial `sinh`, `sinf`, and `sind` symbols are the sine family.
They are not the hyperbolic family. The target hyperbolic H/F/D names are `sinhh`, `sinhf`, and `sinhd`.

## `exp` status transition evidence

The `exp` rows remain `unsupported` until reviewers accept all evidence in this section.
Evidence for one format does not change the status of another format.

The `exp` rows use `exph`, `expf`, and `expd` from the initial API.
These rows require callers to keep IEEE round-to-nearest, ties-to-even active. The manifest records this policy for every `exp` row.

Use this checklist for each proposed `correct` or `bounded` transition:

- [ ] Put the dependency-free algorithm in `zmath/src/scalar.zig`.
- [ ] Identify the public symbol as `exph`, `expf`, or `expd`.
- [ ] Show that the implementation does not call host libm or inspect the process floating-point environment.
- [ ] Approve the exact special-value bit table below for the format.
- [ ] Declare an explicit allowlist of supported target triples and Zig optimization modes. Do not infer support for an unlisted target or mode.
- [ ] Support only caller IEEE round-to-nearest, ties-to-even with gradual underflow under schema version 1.
- [ ] For H, validate all 65,536 binary16 input patterns exactly once.
- [ ] For F or D, accept a hard-case corpus with exact input and expected output bits.
- [ ] Include zeros, infinities, NaNs, overflow edges, underflow edges, and subnormal boundaries in each applicable corpus.
- [ ] Include reduction boundaries, rounding midpoints, and the adjacent representable inputs in each F or D hard-case corpus.
- [ ] Generate each finite oracle result with MPFR at exactly 512 bits and `MPFR_RNDN`.
- [ ] Prove with a 512-bit Arb interval that each finite oracle result rounds to the same target bits.
- [ ] Reject a row when MPFR and Arb disagree or when the Arb interval crosses a rounding boundary.
- [ ] Accept a repository-relative benchmark corpus path, its input selection rule, and its input count.
- [ ] Record benchmark results for every supported target and Zig optimization mode.
- [ ] For `correct`, set every corpus `max_ulp` value to `0`.
- [ ] For `bounded`, approve one finite-result ULP limit before the status change.

The exact `exp` special-value table is:

| Format | `+0` input to output | `-0` input to output | `+infinity` input to output | `-infinity` input to output | Any NaN input `b` to output |
| --- | --- | --- | --- | --- | --- |
| `h` | `0000` to `3c00` | `8000` to `3c00` | `7c00` to `7c00` | `fc00` to `0000` | `b OR 0200` |
| `f` | `00000000` to `3f800000` | `80000000` to `3f800000` | `7f800000` to `7f800000` | `ff800000` to `00000000` | `b OR 00400000` |
| `d` | `0000000000000000` to `3ff0000000000000` | `8000000000000000` to `3ff0000000000000` | `7ff0000000000000` to `7ff0000000000000` | `fff0000000000000` to `0000000000000000` | `b OR 0008000000000000` |

The H corpus is exhaustive evidence, not a sample or benchmark substitute.
The F and D hard-case corpora must name their generation method and immutable artifact paths.
The benchmark corpus measures performance only and cannot replace correctness evidence.
The manifest row must remain `unsupported` while any checklist item is missing or disputed.

## TSV schema

A future corpus file uses UTF-8 text without a byte-order mark.
It uses LF line endings and ends with one LF.
It has one header and no blank lines or comments.
The header contains these tab-separated column names in this order:

```text
op	format	input_bits	output_bits	output_class	max_ulp
```

Each data row has exactly six tab-separated fields:

| Column | Rule |
| --- | --- |
| `op` | One of `exp`, `log`, or `sin` |
| `format` | One of `h`, `f`, or `d` |
| `input_bits` | Exact fixed-width input bits |
| `output_bits` | Exact fixed-width expected output bits |
| `output_class` | One of `normal`, `subnormal`, `zero`, `infinity`, or `qnan` |
| `max_ulp` | A canonical unsigned decimal integer |

Bit strings contain lowercase hexadecimal digits without a `0x` prefix.
Each string has the width required by its format.
Leading zeroes are required.
A parser must reject uppercase digits, signs, separators, prefixes, and incorrect widths.

`max_ulp` uses `0` or a nonzero value without a leading zero.
A `correct` function row requires `max_ulp` equal to `0`.
Special-value rows always use `max_ulp` equal to `0` and require an exact bit match.

Rows use manifest operation order, then manifest format order, then unsigned numeric `input_bits` order.
The tuple `(op, format, input_bits)` must be unique across the complete corpus.
A producer must fail on a duplicate.
A consumer must reject an unsorted or duplicate corpus.

## Exact rounding policy

For a finite mathematical result, round once to the target format.
Use round-to-nearest with ties to an even least-significant significand bit.
Use gradual underflow.
Do not flush subnormal values to zero.
Overflow follows IEEE 754 round-to-nearest behavior.
A nonzero result that rounds to zero keeps the sign of the exact result.
Callers must keep IEEE round-to-nearest, ties-to-even active when they call these `zmath` functions. `zmath` does not read, validate, set, or restore the process floating-point environment (`fenv`). Behavior under other rounding modes is unsupported.

`output_bits` is the expected oracle pattern for every row.
For a `correct` function row, the consumer requires an exact match for every output class.
For a `bounded` function row, the consumer requires an exact match for special values and a ULP distance no greater than `max_ulp` for finite normal or subnormal values.
The ULP distance applies only when both finite results have the same sign. A sign difference fails.

## Special values

These encodings are exact:

| Format | `+0` | `-0` | `+1` | `+infinity` | `-infinity` | Canonical quiet NaN |
| --- | --- | --- | --- | --- | --- | --- |
| `h` | `0000` | `8000` | `3c00` | `7c00` | `fc00` | `7e00` |
| `f` | `00000000` | `80000000` | `3f800000` | `7f800000` | `ff800000` | `7fc00000` |
| `d` | `0000000000000000` | `8000000000000000` | `3ff0000000000000` | `7ff0000000000000` | `fff0000000000000` | `7ff8000000000000` |

For a NaN input, preserve the sign and all payload bits.
Set the quiet bit in the output.
The quiet-bit masks are `0200`, `00400000`, and `0008000000000000` for H, F, and D.
Thus, the required output is the input bit pattern OR the format quiet-bit mask.
A quiet NaN remains unchanged.
A signaling NaN becomes a quiet NaN.

An invalid non-NaN input produces the positive canonical quiet NaN for its format.
No corpus output may encode a signaling NaN.
The `qnan` class requires an exact match of the sign, quiet bit, and payload.

The operation rules are:

| Operation | Exact special-value behavior |
| --- | --- |
| `exp` | `exp(+0)` and `exp(-0)` are `+1`. `exp(+infinity)` is `+infinity`. `exp(-infinity)` is `+0`. |
| `log` | `log(+0)` and `log(-0)` are `-infinity`. `log(+1)` is `+0`. `log(+infinity)` is `+infinity`. A negative non-NaN input produces the canonical quiet NaN. |
| `sin` | `sin(+0)` is `+0`. `sin(-0)` is `-0`. Either infinity produces the canonical quiet NaN. |

The NaN-input rule takes precedence over each operation rule.
The producer encodes exact constants directly and does not ask a host library to choose their bits.

## Fail-closed rules

A producer must stop without changing corpus files when any required fact is uncertain.
Uncertainty includes an oracle disagreement, an Arb interval that spans two target results, and an unknown special-value policy.
A consumer must reject a corpus that disagrees with this document or its manifest.
It must not skip a bad row, substitute a host result, or accept a nearby value.

All nine initial function-format rows start as `unsupported`.
An implementation may exist while its row is `unsupported`. It becomes supported by this contract only when the row changes to `correct` or `bounded`.
Schema version 1 accepts transcendental corpus data only for rows with `correct` or `bounded` status.
